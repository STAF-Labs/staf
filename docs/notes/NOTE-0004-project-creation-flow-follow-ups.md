# Доработка flow создания проекта

Статус: требуется доработка.

Текущий API и многошаговый интерфейс создают проект по основному сценарию, но перед завершением flow
нужно устранить следующие ограничения:

## Выполнено

- начальный статус проекта назначается на backend и не принимается от клиента при создании;
- `licence_name` добавлен в таблицу, модель, API и frontend;
- `dimension_value_ids` возвращается после создания и при последующем получении проекта;
- мастер сохраняет созданный проект поэтапно, используя существующий статус `draft` и процент
  заполненности;
- в мастере можно выбрать автора: личный профиль или активную организацию, где пользователь имеет
  роль `owner` или `maintainer`; backend проверяет членство и запрещает смену автора через обычное
  обновление проекта;
- редактирование релизов реализовано через общую форму создания/редактирования: можно заменить файл,
  изменить название, тип, changelog и release-level filters;
- вкладка релизов в редактировании проекта показывает список релизов с поиском, фильтрами,
  настройкой колонок, сортировкой и кнопкой добавления нового релиза после первого релиза;
- страница просмотра проекта реализована с табами `Обзор`, `Релизы`, `Скриншоты`; правые блоки
  вынесены за пределы табов и доступны во всех вкладках;
- вкладка `Релизы` в просмотре проекта показывает только опубликованные релизы, поддерживает
  read-only список, раскрывающийся summary-блок, скачивание файла и внутреннюю страницу релиза;
- TipTap JSON рендерится read-only без редактора на подтверждении создания проекта, странице
  просмотра проекта, игре, организации, пользователе и changelog релиза;
- вкладка `Участники` в редактировании проекта загружает прямых участников проекта и, для проекта
  организации, участников организации с доступом через роли `owner`/`maintainer`.

## Осталось

- вынести сохранение одного шага проекта, media и project-level dimensions в единую бизнес-операцию
  с откатом изменений текущего запроса и очисткой файлов, созданных в рамках этого запроса, при
  ошибке;
- сделать `summary` обязательным на backend и проверять содержимое `summary` и `description`, а не
  только тип JSON;
- ограничить общий размер multipart-запроса и настроить throttle для загрузки файлов;
- определить и проверить backend-правило выбора конечных значений иерархических dimensions;
- реализовать редактирование информации об участнике проекта: роль, статус и будущие права доступа;
- подключить реальное действие смены статуса проекта вместо заглушки в меню `Ещё`;
- расширить feature-тесты сценариями прав, статусов, ролей организации, некорректных файлов,
  пустых документов и сбоев с откатом.

## Уточнение по частичному сохранению

Частично сохранённый проект — это ожидаемое поведение мастера. После первого содержательного шага
backend создаёт настоящий `Project` со статусом `draft` и `percentage_complete`, чтобы пользователь
мог вернуться после потери соединения, закрытия вкладки или паузы в заполнении.

Проблема не в самом `draft`-проекте, а в частично применённом одном запросе сохранения. Если
пользователь сохраняет шаг, этот конкретный запрос должен завершиться целостно: либо все изменения
шага применены, либо изменения этой попытки не остаются в системе.

Например, если при сохранении шага успели записаться часть media, но затем упала синхронизация
project-level dimensions, пользователь получит ошибку. В такой ситуации уже существующий
`draft`-проект не должен удаляться целиком, но новые файлы и изменения, созданные именно в рамках
упавшего запроса, должны быть откатаны или очищены.

## Предлагаемая доработка

- оставить текущую модель: мастер работает через настоящий `Project` со статусом `draft`, отдельная
  модель `ProjectDraft` не вводится;
- вынести сохранение проекта в отдельную backend-операцию/action, которая создаёт или обновляет
  проект, сохраняет logo/screenshots, синхронизирует project-level dimensions и обновляет
  `percentage_complete`;
- обернуть database-часть операции в транзакцию и явно очищать media/файлы, созданные текущим
  запросом, если после их записи произошла ошибка;
- не удалять существующий `draft`-проект при ошибке обновления шага, а откатывать только изменения
  текущей попытки;
- добавить общий rich-text validator/helper для TipTap JSON, который отличает заполненный документ
  от пустого `{ "type": "doc", "content": [] }` и пустых параграфов;
- сделать `summary` обязательным для шага, где он сохраняется, и обязательным для публикации;
- проверять `description` как заполненный rich-text документ перед публикацией или финальным
  подтверждением, если описание является обязательной частью готового проекта;
- при переводе проекта в `published` запускать строгую проверку готовности проекта: logo,
  `summary`, `description`, обязательные project-level dimensions и остальные required-поля.

Отдельная модель серверного черновика не планируется. Рассмотренное решение зафиксировано как
отклонённое в [`ADR-0006: Серверные черновики создания проектов`](../adr/ADR-0006-project-creation-drafts.md).
