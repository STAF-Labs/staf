# ADR-0005: Микросервис распознавания лицензий

## Статус

Отменено

## Дата

2026-08-03

## Контекст

При создании проекта пользователь прикладывает файл лицензии и указывает ее название.
Поддерживаются текстовые документы и распространенные форматы файлов, включая PDF, DOC и
DOCX. Если лицензия стандартная, например MIT, Apache-2.0 или GPL-3.0, ее название желательно
определять автоматически по содержимому файла.

Основной backend STAF реализован на Laravel. Распознавание лицензии не относится к бизнес-логике
проекта: оно включает извлечение и нормализацию текста, сравнение с корпусом лицензий SPDX и может
потребовать отдельного управления памятью, тайм-аутами и библиотеками обработки документов.

В модели проекта решено хранить только:

- название лицензии;
- исходный файл лицензии в media collection.

Сохранять статус распознавания и диагностические поля в базе данных не требуется. Если лицензия
не распознана, пользователь должен иметь возможность указать название вручную.

## Проблема

Нужно определить, где и на каком языке выполнять автоматическое распознавание лицензии, чтобы не
связывать Laravel-приложение с ресурсоемкой обработкой документов и при этом не усложнять модель
проекта асинхронными статусами.

## Принятое решение

Реализовать отдельный stateless-микросервис распознавания лицензий на Go.

Laravel остается единственной точкой входа для административного frontend и источником истины для
проекта. Браузер не обращается к микросервису напрямую. При выборе файла frontend отправляет его в
Laravel endpoint предварительного распознавания, а Laravel передает содержимое файла сервису.

Базовый контракт сервиса:

```text
POST /v1/licenses/detect
Content-Type: multipart/form-data
file: <binary>

200 OK
{
  "recognized": true,
  "name": "MIT",
  "spdx_id": "MIT",
  "confidence": 0.99
}
```

Если надежного совпадения нет, сервис возвращает `recognized = false`, а `name` и `spdx_id` —
`null`. `confidence` и `spdx_id` используются только для принятия решения и диагностики ответа;
сохранять их в таблице проектов не нужно.

Сервис должен:

- извлечь текст из разрешенного формата;
- нормализовать текст перед сравнением;
- сопоставить его с известными лицензиями SPDX;
- возвращать название только при достижении заданного порога уверенности;
- не сохранять исходные файлы и результаты между запросами;
- ограничивать размер файла, время обработки и объем извлекаемого содержимого.

Для классификации использовать `google/licenseclassifier` как основной кандидат. Окончательный
выбор библиотеки допускается уточнить при прототипировании на реальных файлах без изменения
границ сервиса и его API.

Распознавание выполняется синхронно до сохранения проекта. Состояние загрузки существует только во
frontend. Успешный ответ предварительно заполняет поле названия лицензии, но пользователь может его
изменить. Ошибка, тайм-аут или отсутствие совпадения не блокируют создание проекта: поле остается
доступным для ручного заполнения.

На первом этапе извлечение текста реализуется внутри Go-сервиса. Если качество поддержки PDF, DOC
или DOCX окажется недостаточным, допускается добавить Apache Tika как внутренний sidecar для
извлечения текста. Такое расширение не должно менять публичный контракт между Laravel и сервисом.

## Рассмотренные варианты

### Вариант 1: Обрабатывать лицензии в Laravel/PHP

Плюсы:

- не требуется отдельный сервис;
- проще локальная разработка и развертывание;
- отсутствует сетевой вызов между компонентами.

Минусы:

- тяжелый разбор документов выполняется в процессе основного backend;
- библиотеки классификации лицензий и работы с форматами становятся зависимостями Laravel;
- сложнее независимо ограничивать и масштабировать обработку недоверенных файлов.

Причина отказа:

- распознавание является изолированной вычислительной задачей с отдельным профилем зависимостей и
  надежности.

### Вариант 2: Микросервис на Java с Apache Tika

Плюсы:

- зрелое извлечение текста из PDF, DOC и DOCX;
- единый инструментарий для большого числа форматов документов.

Минусы:

- более тяжелый runtime и больший базовый расход памяти;
- распознавание лицензии все равно требует отдельной реализации или библиотеки;
- для небольшого stateless-сервиса развертывание сложнее, чем одного Go-бинарника.

Причина отказа:

- основной задачей сервиса является классификация лицензий, для которой в Go есть готовые
  специализированные библиотеки. Apache Tika можно добавить отдельно, если это подтвердится
  практическими тестами форматов.

### Вариант 3: Микросервис на Go

Плюсы:

- существуют специализированные классификаторы лицензий;
- сервис собирается в один бинарный файл;
- небольшой runtime и простое горизонтальное масштабирование;
- удобно ограничивать ресурсы обработки отдельно от Laravel.

Минусы:

- извлечение текста из всех поддерживаемых форматов потребует нескольких библиотек;
- появляется отдельный язык, сервис и сетевое взаимодействие;
- качество распознавания необходимо проверить на реальных лицензиях проекта.

Причина выбора:

- вариант соответствует небольшой stateless-задаче, изолирует обработку файлов и оставляет
  возможность позднее подключить более сильный extractor без изменения Laravel API.

### Вариант 4: Асинхронная обработка через очередь

Плюсы:

- запрос пользователя не ожидает завершения распознавания;
- длительные документы можно обрабатывать в фоне.

Минусы:

- требуется хранить статус и результат обработки;
- возможна гонка между автоматическим результатом и ручным изменением названия;
- усложняется интерфейс создания проекта.

Причина отказа:

- файлы ограничены по размеру, распознавание используется как подсказка до сохранения, а отсутствие
  результата не блокирует ручной ввод.

## Последствия

Положительные последствия:

- Laravel не выполняет классификацию и тяжелый разбор документов;
- сбой распознавания не блокирует создание проекта;
- пользователю не нужно вручную вводить название известной лицензии;
- сервис можно развивать и масштабировать независимо;
- в таблицах проекта не появляются технические статусы обработки.

Отрицательные последствия и компромиссы:

- необходимо развертывать и наблюдать дополнительный сервис;
- между Laravel и сервисом появляется внутренний HTTP-вызов;
- интерфейс должен корректно обрабатывать тайм-аут и недоступность сервиса;
- автоматический результат является подсказкой, а не юридическим заключением.

Что нужно учесть в будущем:

- подобрать порог уверенности на наборе реальных файлов;
- версионировать корпус лицензий SPDX;
- проверить PDF, DOC и DOCX с разной кодировкой и структурой;
- не выполнять макросы и активное содержимое документов;
- при добавлении Apache Tika изолировать его от внешней сети и установить лимиты ресурсов;
- добавить метрики времени обработки, ошибок и доли распознанных файлов без сохранения статуса в
  модели проекта.

## Влияние на код

Необходимо:

- создать отдельное Go-приложение сервиса распознавания;
- добавить внутренний HTTP-клиент и endpoint предварительного распознавания в Laravel API;
- настроить URL сервиса, тайм-ауты и порог уверенности через окружение;
- обновить этап лицензии в Vue admin: показывать временную загрузку, заполнять название и сохранять
  возможность ручного редактирования;
- добавить сервис в локальную и production-конфигурацию контейнеров;
- покрыть контракт сервиса, ошибки и fallback интеграционными тестами.

Схема базы данных не изменяется.

## Связанные внешние пакеты

- `google/licenseclassifier` — основной кандидат для классификации;
- `go-enry/go-license-detector` — альтернативный классификатор для сравнения при прототипировании;
- Apache Tika — возможный sidecar для извлечения текста из сложных форматов;
- SPDX License List — источник идентификаторов и эталонных текстов лицензий.

## Примечания

Название, определенное автоматически, всегда можно исправить вручную. Распознавание не должно
интерпретироваться как проверка юридической совместимости лицензии или прав пользователя на
публикацию проекта.
