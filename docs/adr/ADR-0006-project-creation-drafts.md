# ADR-0006: Серверные черновики создания проектов

## Статус

Отклонено

## Дата

2026-08-03

## Контекст

Создание проекта в STAF выполняется в несколько этапов: выбор игры, основные данные и настройки,
описание, лицензия и подтверждение. Сейчас данные мастера существуют только во frontend до
финального запроса создания проекта. Пользователь потеряет заполненные данные при закрытии вкладки,
смене устройства или очистке состояния приложения.

В `ProjectStatus` уже существует значение `draft`. Оно относится к созданному проекту, который еще
не опубликован, но не решает задачу сохранения незавершенного многошагового мастера. Смешивание этих
состояний потребует разрешить неполные записи в `projects` и ослабить доменные ограничения основной
модели.

## Проблема

Нужно определить, как сохранять незавершенный flow создания проекта, чтобы пользователь мог
продолжить его позднее, не превращая неполные данные формы в обычные проекты каталога.

## Принятое решение

Предлагается хранить незавершенное заполнение в отдельной модели `ProjectDraft`, а не в `projects`.

Черновик принадлежит создавшему его пользователю и содержит:

- текущий этап мастера;
- выбранную игру и, при наличии, `game_content_type`;
- предполагаемого владельца проекта;
- JSON payload с введенными полями и выбранными project-level dimensions;
- время последнего изменения;
- срок хранения, если будет включена автоматическая очистка.

Файлы, выбранные до завершения мастера, прикрепляются к `ProjectDraft` через отдельные media
collections. На первом этапе достаточно `logo` и `licence`; поддержка screenshots добавляется к
черновику вместе с их появлением в flow.

Предлагаемый API:

```text
GET    /project-drafts
POST   /project-drafts
GET    /project-drafts/{projectDraft}
PATCH  /project-drafts/{projectDraft}
DELETE /project-drafts/{projectDraft}
POST   /project-drafts/{projectDraft}/complete
```

Frontend создает черновик после выбора игры или первого содержательного изменения и периодически
сохраняет изменения с debounce. Локальное состояние остается рабочей копией формы, а серверный
черновик — источником восстановления между сессиями и устройствами.

При `complete` backend обязан заново проверить весь итоговый payload, права на выбранного владельца,
актуальность `game_content_type`, обязательные dimensions и файлы. Затем backend создает полноценный
`Project`, переносит его media и удаляет черновик. Завершение должно быть защищено от повторного
вызова и выполняться как единая бизнес-операция с компенсационной очисткой файлов при ошибке.

`ProjectStatus::DRAFT` сохраняет отдельное значение: это статус уже созданного проекта. Наличие
`ProjectDraft` не должно влиять на каталог, модерацию, slug проекта или статистику проектов.

Доступ к черновику имеет только создавший его пользователь. Право завершить черновик дополнительно
проверяется по актуальным permissions и выбранному владельцу. Идентификатор черновика нельзя считать
достаточным разрешением на чтение или изменение.

## Рассмотренные варианты

### Вариант 1: Хранить незавершенный мастер в `projects` со статусом `draft`

Плюсы:

- не требуется отдельная сущность;
- существующий `ProjectStatus::DRAFT` можно использовать без нового API;
- media сразу принадлежат проекту.

Минусы:

- обязательные поля проекта придется сделать nullable или заполнять временными значениями;
- неполные проекты попадут в общие запросы, права, статистику и административные операции;
- slug и другие доменные правила будут применяться раньше времени;
- значение `draft` начнет одновременно обозначать неполную форму и полноценный неопубликованный
  проект.

Причина отказа:

- вариант ослабляет инварианты основной модели и смешивает два разных жизненных состояния.

### Вариант 2: Хранить черновик только во frontend

Черновик сохраняется в памяти браузера или `localStorage`.

Плюсы:

- не требуется backend API и новая таблица;
- быстро реализуется;
- не создает серверные записи до отправки формы.

Минусы:

- черновик недоступен на другом устройстве;
- данные могут быть потеряны при очистке браузера;
- неудобно и небезопасно хранить выбранные файлы;
- невозможно централизованно управлять сроком хранения и списком черновиков.

Причина отказа:

- локальное хранение можно использовать как дополнительный кеш, но не как надежный механизм
  восстановления flow.

### Вариант 3: Отдельная модель `ProjectDraft`

Плюсы:

- незавершенные данные изолированы от каталога проектов;
- основная таблица `projects` сохраняет обязательные поля и доменные ограничения;
- черновик можно продолжить на другом устройстве;
- можно независимо настроить доступ, срок хранения и очистку;
- JSON payload позволяет развивать мастер без частых изменений схемы черновиков.

Минусы:

- появляется отдельная модель, API и политика доступа;
- требуется управлять временными media;
- завершение требует переноса данных и файлов;
- нужно определить разрешение конфликтов при одновременном редактировании.

Причина выбора:

- вариант сохраняет чистую модель проекта и дает надежное серверное восстановление многошаговой
  формы.

## Последствия

Положительные последствия:

- пользователь может прервать создание и продолжить его позднее;
- неполные данные не попадают в каталог и модерацию;
- обязательность полей `projects` не ослабляется;
- черновики можно очищать и ограничивать независимо от проектов;
- архитектура подходит для будущих мастеров создания других сущностей.

Отрицательные последствия и компромиссы:

- усложняется flow создания проекта;
- временные файлы занимают место до завершения или очистки черновика;
- frontend должен учитывать сохранение, восстановление и конфликт версий;
- завершение черновика становится отдельной составной операцией.

Что нужно учесть в будущем:

- определить срок хранения и правила автоматической очистки;
- решить, нужен ли пользователю один или несколько черновиков одновременно;
- добавить защиту от перезаписи более новой версии, например через `updated_at` или номер версии;
- определить лимиты количества и общего размера черновиков пользователя;
- не считать сохранение черновика окончательной бизнес-валидацией проекта.

## Влияние на код

Потребуется:

- модель, migration и policy для `ProjectDraft`;
- media collections временных файлов;
- CRUD API черновиков и endpoint завершения;
- action завершения черновика с повторной валидацией, переносом media и защитой от повторного
  выполнения;
- автосохранение и восстановление состояния в Vue admin;
- список или предложение продолжить существующий черновик;
- задача очистки просроченных черновиков и media;
- feature-тесты доступа, автосохранения, восстановления, завершения и очистки.

## Связанные внешние пакеты

- `spatie/laravel-medialibrary` — временные media черновика и перенос файлов в проект;
- `laravel/sanctum` — аутентификация API;
- `spatie/laravel-permission` — разрешение на создание проекта, если оно будет введено в policy.

## Примечания

Решение остается предложенным. Перед реализацией нужно отдельно утвердить срок хранения черновиков,
допустимое количество черновиков на пользователя и правила переноса media.
