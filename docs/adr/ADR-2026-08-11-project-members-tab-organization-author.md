# ADR-2026-08-11: Вкладка участников проекта при авторе-организации

## Статус

Предложено

## Дата

2026-08-11

## Контекст

В админке проекта появилась вкладка `Участники`. Сейчас она показывает автора проекта как карточку
владельца и позволяет приглашать пользователей в `project_members` со статусом `invited` и ролью
`member`.

У проекта при этом уже есть полиморфный автор: личный профиль пользователя или организация. Для
организации есть собственные участники и роли, а права редактирования проекта сейчас проверяются
через владельца проекта и активное членство пользователя в организации с ролью `owner` или
`maintainer`.

Текущая вкладка участников не учитывает сценарий, где автор проекта — организация. В этом случае
карточка автора-организации не является человеком-участником проекта, а реальные люди, которые могут
действовать от имени организации, живут в `organization_members`.

## Проблема

Нужно определить, как вкладка `Участники` должна представлять людей и права доступа, если проект
принадлежит организации, а не личному профилю пользователя.

Если оставить текущую модель отображения, UI будет смешивать разные сущности:

- автора проекта как владельца контента;
- участников организации как людей, которые могут управлять проектом через организацию;
- прямых участников проекта из `project_members`;
- будущие project-level права доступа.

Это создаёт риск неправильных ожиданий: админ может считать, что организация сама является участником
проекта, хотя действия выполняют конкретные пользователи.

## Принятое решение

Вкладку `Участники` нужно доработать как отдельную модель представления доступа к проекту.

Для проекта с автором-пользователем вкладка может показывать этого пользователя как владельца проекта
и прямых участников из `project_members`.

Для проекта с автором-организацией вкладка должна явно учитывать два источника доступа:

- участники организации, которые получают доступ к проекту через роль в организации;
- прямые участники проекта из `project_members`, если проект поддерживает приглашения вне состава
  организации.

UI не должен показывать организацию как обычного человека-участника. Организацию можно показывать как
контекст владения проектом, но карточки участников должны представлять конкретных пользователей.

Backend должен остаться источником истины для прав. Frontend может объединять данные для отображения,
но не должен самостоятельно решать, кто имеет право редактировать проект.

## Рассмотренные варианты

### Вариант 1: Оставить текущий UI без различий между user и organization author

Вкладка всегда показывает `owner_name` как владельца и прямых project members.

Плюсы:

- минимум изменений;
- текущая заготовка продолжает работать для личных проектов.

Минусы:

- организация выглядит как участник-человек;
- не видно реальных пользователей организации, которые управляют проектом;
- будущие права доступа будут сложнее объяснить в UI.

Причина отказа:

- вариант скрывает важное различие между владельцем-контекстом и пользователями, которые имеют
  доступ.

### Вариант 2: Показывать только прямых `project_members`

Вкладка игнорирует автора и участников организации, отображая только записи из `project_members`.

Плюсы:

- простая модель данных;
- карточки всегда относятся к одной таблице.

Минусы:

- владелец личного проекта может исчезнуть из вкладки;
- пользователи с доступом через организацию не будут видны;
- нужно дублировать организационные права в project members или объяснять скрытый доступ отдельно.

Причина отказа:

- вариант не отражает фактические источники доступа к проекту.

### Вариант 3: Разделить источники доступа во вкладке

Вкладка показывает людей, сгруппированных или помеченных по источнику доступа: автор-пользователь,
участник организации, прямой участник проекта.

Плюсы:

- UI показывает конкретных пользователей, а не абстрактную организацию;
- не теряется доступ через `organization_members`;
- проще добавить будущие project-level права доступа без смешивания сущностей.

Минусы:

- API и frontend должны отдавать/объединять больше данных;
- нужно определить правила конфликтов, если пользователь одновременно участник организации и прямой
  участник проекта.

Причина выбора:

- это самый честный вариант для модели STAF, где проекты могут принадлежать пользователям и
  организациям.

## Последствия

Положительные последствия:

- вкладка `Участники` будет корректно отображать людей с доступом к проекту;
- организация останется контекстом владения, а не псевдо-участником;
- будущие права доступа можно будет развивать поверх понятной модели.

Отрицательные последствия и компромиссы:

- потребуется доработать API участников проекта;
- нужно решить, как показывать пользователя, если он имеет доступ сразу через организацию и напрямую;
- для organization author потребуется загрузка участников организации или отдельный агрегированный
  endpoint.

Что нужно учесть в будущем:

- прямое приглашение участника в проект не должно неявно добавлять его в организацию;
- удаление или заморозка участника организации должна влиять на доступ к проекту через организацию;
- UI должен различать `invited` project member и active organization member;
- действия редактирования роли и прав должны проверяться backend policies.

## Влияние на код

Нужно учесть:

- `ProjectPolicy` и будущие project member policies;
- `ProjectController` endpoints для participants/members;
- `ProjectMemberResource` и возможный агрегированный resource для отображения доступа;
- `OrganizationMember` и роли организации;
- Vue admin вкладку `Участники`;
- контракты `packages/contracts`;
- feature-тесты для user author и organization author.

## Примечания

Текущая реализация вкладки `Участники` является UI/API-заготовкой. Перед развитием редактирования
ролей и прав нужно отдельно спроектировать отображение участников для проектов, где автором является
организация.
