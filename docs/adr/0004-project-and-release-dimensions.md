# ADR 0004: Значения dimensions на уровне проекта и релиза

## Статус

Принято

## Дата

2026-08-03

## Контекст

В STAF глобальные типы контента связываются с конкретными играми через `game_content_types`.
Dimensions принадлежат такой связке и описывают доступные характеристики проектов и релизов.

Часть характеристик постоянна для проекта и не должна повторяться в каждом релизе:

- категория;
- жанр;
- тематика;
- другие свойства самого проекта.

Другие характеристики описывают совместимость или особенности конкретного релиза и могут
изменяться между версиями:

- версия игры;
- загрузчик или API;
- платформа, если она зависит от релиза;
- другие release-specific свойства.

Существующая схема содержит только `project_release_dimension_values`. Она позволяет связывать
значения с релизами, но вынуждает дублировать постоянные характеристики проекта в каждом релизе.

## Проблема

Нужно определить, на каком уровне выбираются значения dimensions, чтобы постоянные свойства
проекта хранились один раз, а совместимость и другие изменяемые характеристики могли задаваться
отдельно для каждого релиза.

При этом необходимо сохранить контекстную модель:

```text
games -> game_content_types -> dimensions -> dimension_values
```

Значения проекта или релиза не должны ссылаться на dimensions другой игры или другого типа
контента.

## Принятое решение

Добавить в `dimensions` обязательное поле `applies_to` со значениями:

- `project` — значение выбирается один раз для проекта;
- `release` — значение выбирается отдельно для каждого релиза.

Использовать две отдельные связующие таблицы:

```text
project_dimension_values
  project_id
  dimension_value_id

project_release_dimension_values
  project_release_id
  dimension_value_id
```

Для каждой таблицы должен быть уникальный индекс по паре внешних ключей.

Примеры рекомендуемого уровня:

| Dimension | `applies_to` |
| --- | --- |
| Категория | `project` |
| Жанр | `project` |
| Тематика | `project` |
| Версия игры | `release` |
| Загрузчик/API | `release` |
| Платформа | Определяется контекстом типа контента |

`applies_to` является свойством конкретной dimension внутри `game_content_type`. Одинаковое
название фильтра в разных играх или типах контента может иметь разный уровень применения.

Backend обязан проверять при сохранении значений:

- dimension относится к тому же `game_content_type`, что и проект;
- `project_dimension_values` принимает только dimensions с `applies_to = project`;
- `project_release_dimension_values` принимает только dimensions с `applies_to = release`;
- для `selection_mode = single` выбрано не более одного значения;
- для `selection_mode = multiple` разрешено несколько значений;
- все активные обязательные dimensions соответствующего уровня заполнены;
- выбранные `dimension_values` принадлежат своим dimensions и активны.

Изменение `applies_to` для dimension, которая уже используется проектами или релизами, нельзя
выполнять без явной миграции существующих связей. Обычное редактирование такой dimension должно
быть заблокировано с конфликтом `409`.

## Рассмотренные варианты

### Вариант 1: Хранить все значения на релизе

Плюсы:

- соответствует текущей таблице `project_release_dimension_values`;
- не требуется новая pivot-таблица.

Минусы:

- категории, жанры и тематики дублируются в каждом релизе;
- релизы одного проекта могут случайно получить разные постоянные характеристики;
- проект без релиза невозможно полноценно классифицировать.

Причина отказа:

- модель смешивает свойства проекта с совместимостью конкретного релиза.

### Вариант 2: Хранить все значения на проекте

Плюсы:

- простая форма проекта;
- отсутствует дублирование между релизами.

Минусы:

- невозможно корректно указать разные версии игры или загрузчики для разных релизов;
- совместимость проекта становится неточной.

Причина отказа:

- release-specific характеристики являются частью конкретного релиза.

### Вариант 3: Разделить dimensions по уровню применения

Плюсы:

- постоянные характеристики хранятся один раз;
- каждый релиз получает собственную совместимость;
- проект можно классифицировать до создания первого релиза;
- правила выбора остаются частью contextual dimension.

Минусы:

- появляется дополнительная pivot-таблица;
- формы проекта и релиза должны загружать разные наборы dimensions;
- изменение уровня используемой dimension требует миграции данных.

Причина выбора:

- вариант отражает различия между сущностью проекта и его публикуемыми версиями.

## Последствия

Положительные последствия:

- категории, жанры и тематики не дублируются между релизами;
- версии игры и другие параметры совместимости могут отличаться у каждого релиза;
- каталог может фильтровать как проекты, так и совместимые релизы;
- обязательность и режим выбора остаются единообразными.

Отрицательные последствия и компромиссы:

- API должен валидировать не только идентификаторы, но и полный контекст связей;
- изменение `game_content_type` проекта потребует повторной проверки или очистки выбранных
  значений;
- запросы каталога должны учитывать оба уровня dimensions.

Что нужно учесть в будущем:

- определить поведение каталога, если одному проекту подходят несколько релизов;
- определить правила наследования release-значений при создании нового релиза;
- предусмотреть безопасный перенос dimension между уровнями.

## Влияние на код

Необходимо:

- добавить enum уровня применения dimension;
- добавить `dimensions.applies_to` с индексом;
- создать модель и миграцию `project_dimension_values`;
- добавить связи к моделям `Project`, `ProjectRelease`, `Dimension` и `DimensionValue`;
- обновить API создания и редактирования dimensions;
- добавить API выбора project-level значений в форме проекта;
- реализовать API релизов и выбор release-level значений;
- обновить импорт dimensions колонкой `applies_to`;
- добавить проверки `single`, `multiple`, `is_required`, `is_active` и контекста
  `game_content_type`;
- покрыть правила feature-тестами;
- обновить Vue admin для раздельного управления значениями проекта и релиза.

## Примечания

Это решение не делает dimensions глобальными. Они по-прежнему принадлежат конкретному
`game_content_type`; `applies_to` определяет только место выбора значения.
