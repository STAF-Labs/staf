# ADR-2026-08-08: Автор проекта и права организаций

## Статус

Принято

## Дата

2026-08-08

## Контекст

Проект STAF может принадлежать пользователю или организации. Эта связь уже хранится через
полиморфные поля `projects.ownerable_type` и `projects.ownerable_id`.

Многошаговый мастер создания проекта ранее всегда выбирал текущего пользователя, хотя backend
допускал организацию. При этом любой активный участник организации, включая роли `member` и
`reader`, мог отправить организацию как владельца. Обычное обновление проекта также принимало поля
владельца и позволяло неявно переносить проект.

В каталоге автор отображается как `by {author}`. Для личного проекта это имя пользователя, для
проекта организации — название организации.

## Проблема

Нужно определить, кого можно выбрать автором проекта, какие участники могут действовать от имени
организации и можно ли менять автора через обычное редактирование проекта.

## Принятое решение

В форме создания проекта перед полем «Название» используется селектор «Автор».

В селекторе доступны:

- личный профиль текущего пользователя;
- активные организации, в которых пользователь имеет активное членство с ролью `owner` или
  `maintainer`.

Роли `member` и `reader` не дают права создавать проекты от имени организации. Приглашенные и
приостановленные членства, а также заблокированные или приостановленные организации не дают такого
права.

Backend остается источником истины. Список вариантов автора и сохранение проекта проверяются одной
`ProjectPolicy`. Значение, отправленное клиентом, нельзя считать разрешенным только потому, что оно
присутствует в форме.

После первого сохранения проекта автор фиксируется. Обычный endpoint обновления проекта не принимает
`ownerable_type` и `ownerable_id`. Если перенос проекта понадобится, для него создается отдельная
операция с отдельным правилом авторизации, аудитом и проверками обеих сторон.

API проекта возвращает единое поле `owner_name`: display name или username пользователя либо
название организации. Карточка каталога использует это значение для `by {author}`.

## Рассмотренные варианты

### Вариант 1: Всегда использовать текущего пользователя

Плюсы:

- не нужен выбор автора;
- минимальная авторизация.

Минусы:

- организация не может выступать автором собственного проекта;
- существующая полиморфная модель владельца не используется полностью.

Причина отказа:

- вариант не поддерживает публикацию проектов организациями.

### Вариант 2: Разрешить всем активным участникам организации

Плюсы:

- простое правило;
- меньше настроек ролей.

Минусы:

- роли `member` и `reader` получают право представлять организацию;
- чтение или обычное участие не должны автоматически давать право создавать публичные сущности от
  имени организации.

Причина отказа:

- правило дает более широкие полномочия, чем подразумевают роли.

### Вариант 3: Разрешить ролям owner и maintainer

Плюсы:

- право соответствует ответственности управляющих ролей;
- `member` и `reader` остаются безопасными ролями без права представлять организацию;
- правило можно позднее расширить отдельными правами внутри организации.

Минусы:

- обычный участник должен обратиться к управляющему организации;
- изменение матрицы ролей требует обновления policy и тестов.

Причина выбора:

- это безопасный исходный набор ролей без преждевременной системы индивидуальных прав внутри
  организации.

## Последствия

Положительные последствия:

- проекты могут публиковаться от имени пользователя или организации;
- UI показывает только доступных авторов;
- подмена автора прямым API-запросом блокируется backend;
- карточка проекта одинаково отображает пользователей и организации;
- обычное редактирование не используется для переноса владения.

Отрицательные последствия и компромиссы:

- создание проекта зависит от состояния членства и организации;
- при изменении роли или статуса организации доступ может исчезнуть;
- перенос существующего проекта потребует отдельного flow.

Что нужно учесть в будущем:

- определить процесс переноса проекта между авторами;
- решить, нужны ли организации настраиваемые права для роли `member`;
- добавить аудит действий, выполненных пользователем от имени организации.

## Влияние на код

- `ProjectPolicy` проверяет автора и роль в организации;
- endpoint вариантов автора фильтрует организации через те же правила;
- `StoreProjectRequest` требует аутентифицированного пользователя;
- обычный update не принимает поля автора;
- Vue admin хранит выбранного автора в состоянии мастера и блокирует поле после первого сохранения;
- feature-тесты покрывают личного автора, роли организации, статусы и защиту от переноса.

Изменение схемы базы данных не требуется.
