# ADR для STAF

Используй этот skill, когда нужно создать или обновить Architecture Decision Record для проекта STAF.

STAF — долгосрочная игровая community-платформа на Laravel + Vue, поэтому архитектурные решения должны учитывать масштабируемость, модульность, поддержку разных типов контента, безопасность, админку, публичный frontend и развитие проекта без крупных переделок.

## Когда нужен ADR

Создавай ADR, если задача затрагивает архитектуру проекта.

ADR нужен, когда:

- выбирается структура моделей или таблиц;
- меняется архитектура пользователей, организаций, ролей или прав;
- проектируется каталог игр, проектов, модов, релизов, файлов, категорий или фильтров;
- выбирается подход к админке;
- выбирается frontend-архитектура;
- выбирается способ авторизации или разграничения доступа;
- добавляется внешний пакет, который влияет на архитектуру;
- меняется способ хранения медиафайлов;
- меняется структура API;
- появляется решение, которое будет трудно поменять позже;
- есть несколько нормальных вариантов и нужно зафиксировать выбранный.

ADR не нужен, если изменение мелкое и не влияет на архитектуру:

- исправление CSS;
- правка текста;
- мелкий bugfix;
- простая правка валидации;
- добавление одного очевидного поля без архитектурных последствий.

## Где хранить ADR

Все ADR хранятся в директории:

```text
docs/adr/
```

Шаблон находится здесь:

```text
docs/adr/_template.md
```

## Формат имени файла

Файл называй по шаблону:

```text
ADR-YYYY-MM-DD-title-kebab-case.md
```

Примеры:

```text
ADR-2026-07-17-project-catalog-architecture.md
ADR-2026-07-17-admin-frontend-architecture.md
ADR-2026-07-17-organization-permissions.md
```

Название должно быть коротким, понятным и в `kebab-case`.

## Язык

Пиши ADR на русском языке.

Стиль — простой и практичный. Не делай текст слишком академическим.

## Статусы

Используй такие статусы:

- `Предложено`
- `Принято`
- `Отклонено`
- `Устарело`
- `Заменено`

Новый ADR обычно создаётся со статусом `Предложено`, если пользователь явно не сказал, что решение уже принято.

Статус ADR — единственный авторитетный индикатор его текущего фактического состояния. Формулировки
в остальных разделах сохраняют контекст той временной линии, в которой решение предлагалось и
описывалось. Например, отклонённый ADR может по-прежнему содержать раздел «Принятое решение» и
формулировки о предлагаемой реализации — это не делает решение действующим.

## Правила написания

ADR должен объяснять не только итоговое решение, но и почему оно выбрано.

Обязательно указывай:

- контекст;
- проблему;
- принятое решение;
- рассмотренные варианты;
- последствия;
- влияние на код;
- связанные внешние пакеты;
- связанные ADR.

Раздел `Рассмотренные варианты` обязателен.

Нельзя писать ADR только как описание итогового решения без альтернатив.

## Уровень детализации

Делай ADR средней подробности.

Нужно объяснить достаточно, чтобы через несколько месяцев было понятно:

- почему решение приняли;
- какие варианты были;
- почему отказались от других вариантов;
- какие компромиссы появились;
- что нужно учитывать дальше.

Не превращай ADR в полное техническое ТЗ, если пользователь отдельно этого не просил.

## Как работать с существующими ADR

Не изменяй содержание существующего ADR без явного запроса пользователя. Не актуализируй контекст,
решение, варианты, последствия, влияние на код или исторические формулировки по текущей реализации.
При чтении и аудите определяй состояние ADR по полю статуса, а не по формулировкам внутри документа.

Если пользователь явно просит изменить только статус ADR, меняй только статус и сохраняй всё
остальное содержание без изменений.

Не редактируй принятый ADR так, будто решение всегда было другим.

Если решение изменилось:

1. Создай новый ADR.
2. Укажи, какой ADR он заменяет.
3. В старом ADR можно изменить только статус на `Заменено`, если это требуется проектными правилами.

## Внешние пакеты

Если решение связано с внешними пакетами, укажи их явно.

Примеры:

```text
spatie/laravel-permission
spatie/laravel-medialibrary
laravel/sanctum
vue-router
pinia
```

Если пакетов нет, пиши:

```text
Не применимо.
```

## Что учитывать именно для STAF

При создании ADR всегда проверяй, не противоречит ли решение принципам STAF:

- платформа не должна быть заточена только под Minecraft;
- архитектура должна поддерживать разные игры и разные типы контента;
- админка может быть отдельным Vue-приложением;
- backend остаётся источником истины для прав и безопасности;
- Spatie Permission можно использовать для ролей и прав;
- Spatie Media Library можно использовать для медиа;
- не добавлять сложные абстракции раньше необходимости;
- не делать временные решения, которые придётся быстро переписывать.

## Результат работы

Когда пользователь просит создать ADR:

1. Уточни решение, если данных недостаточно.
2. Если данных достаточно — создай файл по шаблону.
3. Не меняй несвязанные файлы.
4. В конце кратко напиши, какой ADR создан и что он фиксирует.
